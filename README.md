# Bsky Live Wall

Bluesky の特定ハッシュタグ付き投稿を **Jetstream v2** からリアルタイム受信し、
イベント会場のモニター／スクリーンに大きく流し続けるライブウォールです。

- サーバーサイドで動作する Node.js アプリ 1 プロセスで完結します。
- 会場モニターはブラウザを全画面にするだけ。ページ更新なしで流れ続けます。
- Bluesky アカウントの認証情報は不要です (公開エンドポイントのみを使用)。

## 必要環境

- **Node.js 24 以上** (テナント設定の永続化に標準の `node:sqlite` を使うため)
- pnpm (npm / yarn でも可)
- 会場 PC からインターネットへの WebSocket 接続 (`wss://jetstream*.bsky.network`)

## セットアップ

```bash
git clone <このリポジトリ>
cd bsky-live-wall
pnpm install
cp .env.example .env
```

`.env` の `HASHTAGS` をイベントのハッシュタグに書き換えます。
未設定のままでも起動でき、その場合は管理画面から設定します。

```dotenv
HASHTAGS=myevent2026
EVENT_TITLE=My Event 2026
EVENT_SUBTITLE=Tokyo / Hall A
```

## 起動

```bash
# 開発 (ファイル変更で自動再起動)
pnpm dev

# 本番
pnpm build
pnpm start
```

| URL | 用途 |
| --- | --- |
| `http://localhost:3000/wall` | **会場モニター用**。ブラウザで開いて F11 で全画面にする |
| `http://localhost:3000/wall/<id>` | 2 つ目以降のウォール (下記参照) |
| `http://localhost:3000/e/<EVENT_ID>/wall` | イベントを明示した経路 (下記参照) |
| `http://localhost:3000/admin` | 運営用の管理画面 |
| `http://localhost:3000/api/health` | ヘルスチェック |

## 会場モニターの操作

会場係が過去の投稿を遡って確認できます。

| 操作 | 動作 |
| --- | --- |
| マウスホイール / トラックパッド | 過去の投稿へスクロール |
| スクロール中に新着が届いた場合 | 読んでいる位置は動かず、画面下部に「N 件の新着」が出る |
| 「N 件の新着」をクリック | 先頭 (最新) へ戻る |
| 60 秒間操作しない | 自動で先頭へ戻り、新着への追従を再開する |

先頭にいる間は常に最新が追従表示されるため、通常の運用では操作は不要です。
遡れる範囲は `WALL_MAX_CARDS` (既定 40 件) までです。

## 会場モニターの表示オプション

URL クエリで `.env` の設定を上書きできます。

| クエリ | 例 | 説明 |
| --- | --- | --- |
| `columns` | `?columns=2` | カラム数 (`1` で縦流れ) |
| `max` | `?max=60` | DOM 上に保持する最大カード数 |
| `theme` | `?theme=light` | ライトテーマ |
| `noimages` | `?noimages=1` | 画像を表示しない |
| `demo` | `?demo=1` | ダミー投稿で表示確認 (リハーサル用) |

イベント名に「Bluesky」が含まれる場合、その部分を Bluesky のロゴアイコン
(Font Awesome のブランドアイコン、ブランドカラー `#0085ff`) で表示します。
テナント単位の設定で、管理画面の「イベント情報」、または `.env` の
`SHOW_BLUESKY_LOGO` で切り替えられます (既定は表示)。

タイトルのグラデーションをゆっくり流すこともできます (既定は止める)。同じく
「イベント情報」か `ANIMATE_TITLE_GRADIENT` で切り替えます。端末が「動きを減らす」
設定のときは、有効にしていても自動的に止まります。

ヘッダの監視語表示と右上の時計は、管理画面の「会場モニター」からウォールごとに
切り替えられます。

### 画面モード (待機・休憩・終演)

会場の進行に合わせて、モニターの表示をウォールごとに切り替えられます。管理画面の
「会場モニター」で、プレビューを見ながら設定します。

| モード | 表示 |
| --- | --- |
| 通常 | 投稿カードが流れる。投稿が 1 件も無いときだけ待機画面になる |
| 待機 | 開演前の案内。見出しと補足は編集でき、既定は「ハッシュタグはこちら」 |
| 休憩 | 休憩の見出しと再開予定を大きく出す |
| 終演 | 締めの挨拶とハッシュタグ、補足 |

- どのモードでも受信と承認は続きます。通常へ戻すと、その間に届いた投稿がそのまま流れます
- 待機モードは「投稿が届いたら通常へ戻す」を有効にしておくと、最初の投稿で自動的に戻ります
  (休憩・終演は運営が戻すまで保ちます)
- 通常モード以外では、QR コードなどの画像を 1 枚出せます (PNG / JPEG / WebP、2 MB まで)。
  位置と大きさ、添える一言を選べます。実体は `UPLOAD_DIR` にファイルとして保存します

| 設定 | 既定 | 表示 |
| --- | --- | --- |
| ヘッダに監視語を表示する | オン | オフにするとヘッダから監視語が消える |
| ヘッダにキーワードも表示する | **オフ** | キーワードは投稿者に付けてもらうものではないため、既定では会場に出さない |

待機画面のハッシュタグ表示はこの設定に関わらず出ます。投稿者に付けてもらう必要が
あるためです。


| 設定 | 表示 |
| --- | --- |
| 時計を表示する: オフ | 時計そのものを出さない |
| 秒を表示する: オン | `12:34` の右下に秒を小さく添える |
| 秒を表示する: オフ | 秒は出さず、区切りの「:」が 1 秒ごとに点滅する |

## 設定

すべて `.env` で指定します。項目の一覧と既定値は [`.env.example`](./.env.example) を参照してください。
主なものは以下です。

| 変数 | 既定値 | 説明 |
| --- | --- | --- |
| `HASHTAGS` | 空 | 監視するハッシュタグ (カンマ区切りで複数可)。空でも起動する |
| `KEYWORDS` | 空 | ハッシュタグ以外に監視するキーワード (本文の部分一致) |
| `KEYWORD_REQUIRE_APPROVAL` | `true` | キーワードだけで一致した投稿を承認待ちに回すか (ウォール・監視語ごとに上書き可) |
| `MODERATION_MODE` | `open` | `approve` にすると運営が承認した投稿だけを表示 (ウォールごとに上書き可) |
| `NG_WORDS` / `NG_PATTERNS` | 空 | 除外する語 / 正規表現 |
| `BLOCK_ACTORS` | 空 | 除外する DID / ハンドル |
| `ALLOW_REPLIES` | `true` | リプライを表示するか |
| `FILTER_LABELED` | `true` | 成人向けラベル付き投稿を除外するか |
| `WALL_COLUMNS` | `1` | カラム数。`1` で縦に流れる。`2` 以上で横並びのグリッド |
| `WALL_MAX_CARDS` | `40` | DOM 上に保持する最大カード数。スクロールで遡れる範囲 |
| `SHOW_BLUESKY_LOGO` | `true` | イベント名の「Bluesky」をロゴアイコンで表示するか (テナント単位) |
| `ANIMATE_TITLE_GRADIENT` | `false` | タイトルのグラデーションを動かすか (テナント単位) |
| `BACKFILL_PRESETS` | `30,120,360,1440` | 管理画面の「遡る時間」の候補 (分)。テナントごとに足し引きできる |
| `UPLOAD_DIR` | `./data/uploads` | 会場モニターに出す任意画像の保存先 |
| `WALL_SHOW_CLOCK` | `true` | 会場モニター右上の時計を表示するか (ウォールごとに上書き可) |
| `WALL_SHOW_SECONDS` | `true` | 時計に秒を表示するか (ウォールごとに上書き可) |
| `ADMIN_TOKEN` | 空 | 管理 API のトークン。空の場合は localhost からのみ操作可。**リモート公開時は必須** |
| `TRUST_PROXY` | `false` | リバースプロキシ配下で `true`。実クライアント IP を判定し、トークンを必須にする |
| `ADMIN_SESSION_TTL_HOURS` | `12` | 管理セッションの有効時間 |
| `AUTH_MODE` | `token` | `oauth` で Bluesky アカウントによるログイン。`both` で併用 |
| `PUBLIC_URL` | 空 | OAuth 使用時に必須。公開 URL |
| `ADMIN_ACTORS` | 空 | 管理を許可するアカウント (ハンドル / DID)。最初の 1 人を通す入口。multi では招待したメンバーも自動で通る |
| `STARTUP_BACKFILL_MINUTES` | `0` | 起動時に遡る分数。0 で無効 (管理画面から任意に実行できる) |

## 仕組み

```text
Bluesky --(WebSocket: Jetstream v2)--> [ingest] タグ判定 -> モデレーション -> リングバッファ
                                                                       |
                                          [server] Fastify --(SSE)--> 会場モニター / 管理画面
```

- タグ判定は投稿レコードの `facets` (richtext tag)、`tags` フィールド、本文中の `#タグ` の 3 経路を
  NFKC 正規化 + 小文字化して照合します。日本語タグにも対応します。
- ハッシュタグ以外のキーワード (本文の部分一致) も監視できます。詳細は下記を参照してください。
- 投稿の削除 (`delete` コミット) を受信すると、会場モニターからも即座に取り下げ、
  ヘッダの表示件数からも差し引きます。運営が非表示にした投稿も同様です
  (復元すると戻ります)。画面の全消去では件数は減りません。
- 起動時は `STARTUP_BACKFILL_MINUTES` の分だけ過去に遡って再生し、開始直後から画面が埋まった
  状態にします。**この再生はライブ受信とは別の接続で並行して行う**ため、起動直後の新着投稿が
  遅れることはありません。詳細は [バックフィル](#バックフィル起動前の投稿を拾う) を参照してください。
- 投稿者のプロフィール (表示名・アバター) は公開 AppView から非同期に取得し、解決後に差分だけを配信します。
  取得できなくても投稿の表示は止まりません。

詳細は [docs/architecture.md](./docs/architecture.md) を参照してください。

## 運用モード

用途が異なる 2 つの動作形態があります。`.env` の `MULTI_TENANT` で切り替えます。

| | 単一テナント (既定) | マルチテナント |
| --- | --- | --- |
| 用途 | 会場 PC での 1 イベント運用 | 共有サービス |
| `MULTI_TENANT` | `false` | `true` |
| 設定の出どころ | `.env` | `.env` + `DATA_FILE` に永続化 |
| 認証 | トークン / OAuth どちらも可 | **OAuth 必須** |
| 会場モニター | `/wall`, `/wall/<wallId>` | `/e/<tenant>/wall/<wallId>` |
| 管理画面 | `/admin` | `/admin` (ログイン後にテナントを選択)<br>`/e/<tenant>/admin` (直リンク) |

単一テナントでは `/e/<EVENT_ID>/...` の形も使えます (別名)。
マルチテナントではテナントを省略できないため、`/wall` は `/admin` へ転送されます。

**マルチテナントモードは実装途中です。** 永続化層まで実装済みで、テナントごとの
ウォール管理は未対応です。起動時に警告が出ます。

## 複数モニター (マルチウォール)

モニターごとに別の語を拾えます。メイン画面は告知タグ、サブ画面は質問タグ、
別画面はスポンサー名のキーワード、といった使い分けができます。

```text
/wall           メイン    #myevent2026
/wall/qa        Q&A       #質問
/wall/sponsor   スポンサー  キーワード: 製品名
```

ウォールは管理画面から作成・改名・削除できます (最大 10 個)。

URL は 2 通りあり、どちらでも同じ画面が開きます。

```text
/wall/<wallId>                短い経路 (会場で伝えやすい)
/e/<EVENT_ID>/wall/<wallId>   イベントを明示した経路
```

イベントの階層は、将来 1 台のサーバーで複数イベントを扱えるようにするために
今から用意してあるものです。現状は `.env` の `EVENT_ID` (既定 `default`) 1 つだけを
受け付け、それ以外の ID は 404 になります。詳細は
[docs/architecture.md](./docs/architecture.md) の「URL 空間」を参照してください。
`.env` から作られる既定ウォール (`main`) は削除できません。

| 区分 | 内容 |
| --- | --- |
| ウォールごとに独立 | 監視語 / 投稿バッファ / 承認待ち / 表示設定 / 承認モード |
| **全ウォール共通** | ブロック / NG ワード / モデレーションリスト / 一時停止 / Jetstream 接続先 |

モデレーションを共通にしているのは、**荒らしを 1 回ブロックすればすべてのモニターから
消える**ようにするためです。逆に、一時停止も全画面に効きます。

Jetstream への接続はウォールが増えても 1 本のままです。受信した投稿を各ウォールの
監視語と突き合わせて振り分けるため、ウォールを増やしても通信量は変わりません。

## キーワード監視 (ハッシュタグ以外)

ハッシュタグに加えて、本文中の任意の文字列を監視できます。
管理画面で「キーワードとして追加する」にチェックを入れるか、`.env` に書きます。

```dotenv
KEYWORDS=基調講演,keynote
```

**ハッシュタグとキーワードは性質が違います。**

| | ハッシュタグ | キーワード |
| --- | --- | --- |
| 投稿者の意思 | 「この場に出す」と明示している | イベントを認識していない可能性がある |
| 一致方法 | タグの完全一致 | 本文の部分一致 |
| 既定の扱い | そのまま表示 | **承認待ちに回す** |

キーワード一致は、イベントを知らない第三者の投稿を会場スクリーンに映してしまう
可能性があります。そのため、**ハッシュタグが付いておらずキーワードだけで一致した投稿は、
既定で承認待ち**に入り、運営が承認したものだけが表示されます。

```dotenv
# 承認を挟まずに表示したい場合 (会場の性質をよく考えたうえで)
KEYWORD_REQUIRE_APPROVAL=false
```

キーワードは 2 文字以上、監視対象は合計 20 件までです。

### 承認要否はウォールごと・監視語ごとに変えられる

`.env` (テナント設定) は既定値にすぎません。管理画面から、ウォール単位と監視語単位で
上書きできます。意図して設定したキーワードは承認なしで流し、広く拾う語だけ承認待ちに
回す、といった運用ができます。

| 設定する場所 | 選べる値 | 意味 |
| --- | --- | --- |
| ウォールの承認モード | テナント設定に従う / 公開 / 承認制 | 承認制にすると、このウォールに一致した投稿はすべて承認待ち |
| ウォールのキーワードのみ一致 | テナント設定に従う / 承認待ちにする / そのまま表示する | ハッシュタグの付かない一致の既定の扱い |
| 監視語ごと | ウォールの設定に従う / 必ず承認待ちにする / 承認なしで表示する | その語に一致した投稿だけの扱い |

判定の優先順位は次のとおりです。

1. ウォールの承認モードが「承認制」なら、語の設定によらず必ず承認待ち
   (会場のポリシーを語ごとの設定で穴あきにしないため)
2. 一致した語に「必ず承認待ちにする」があれば承認待ち
3. ハッシュタグが付かずキーワードだけで一致した投稿は、一致したキーワードが
   すべて「承認なしで表示する」なら即時表示。そうでなければウォールの設定に従う
4. それ以外は即時表示

承認の設定を変えられるのはオーナーだけです (下の「権限」を参照)。

承認が不要になる向きに設定を変えた場合 (承認制 → 公開、キーワードのみ一致を
「そのまま表示する」へ、語に「承認なしで表示する」を指定)、そのとき承認待ちに
残っていた投稿はその場で表示へ移ります。却下済みの投稿は承認待ちに残らないため
戻りません。逆に設定を厳しくしても、すでに表示した投稿は取り下げません
(会場スクリーンから投稿が消えるのは運営が非表示にしたときだけにするため)。

### 除外キーワード (ネガティブワードを拾わない)

監視語に一致していても、本文に「除外キーワード」を含む投稿はそのウォールでは拾いません。
管理画面の「承認と除外」からウォールごとに設定します (オーナーのみ)。

| 扱い | 既定 | 動作 |
| --- | --- | --- |
| 自動で非承認にする | ✅ | 受信した時点で捨てる。承認待ちにも「直近の投稿」にも残らない |
| 承認待ちに回す | | 運営が判断する。却下した投稿は「非表示にした投稿」にも残さない |

- **承認が不要な設定 (公開モード / 語ごとの「承認なしで表示する」) でも表示しません。**
  除外の判定はすべての承認設定より優先します
- 却下した投稿を復元できないのは意図的です。ネガティブワードを含む文面を運営が
  見続けることによる負担を減らすためです
- 除外キーワードそのものは会場モニターへ送りません (`WallState` に含めません)。
  監査ログにも語は残さず、件数と扱いだけを記録します

`.env` の `EXCLUDE_WORDS` は既定ウォールの初期値です。テナント全体に効く
`NG_WORDS` / `NG_PATTERNS` は従来どおり受信段階で破棄します。

## 権限 (オーナーとモデレーター)

モデレーターは会場で流れているものを見て判断する役割です。設定はオーナーが持ちます。
管理画面はこの線でメニュー自体を出し分け、サーバー側でも同じ判定をします。

| | モデレーター | オーナー |
| --- | --- | --- |
| 承認待ち / 直近の投稿を見る | ✅ | ✅ |
| 承認・却下・非表示・復元・投稿者のブロック | ✅ | ✅ |
| 会場モニターの画面モード切り替え (通常 / 待機 / 休憩 / 終演) | ✅ | ✅ |
| 配信の一時停止・再開 | ✅ | ✅ |
| 監視語を見る | ✅ (読み取り専用) | ✅ |
| 監視語・除外キーワードの変更 | | ✅ |
| 画面モードの文言・画像・ヘッダ / 時計の設定 | | ✅ |
| 表示中の投稿の全消去 | | ✅ |
| イベント情報・NG ワード・受信設定・取り込みの実行 | | ✅ |
| モデレーションリストの購読・解除 | | ✅ |
| ウォールの作成・改名・削除 | | ✅ |
| メンバーの追加・役割変更・削除、セッションの失効 | | ✅ |

システム管理者 (`SYSTEM_ADMINS`) はすべてのテナントでオーナー相当です。

### 承認待ちの投稿はどこで確認するか

管理画面の「承認待ち」パネルに入ります。**ウォールごとに独立**していて、
会場モニターには一切表示されません。

| 操作 | 結果 |
| --- | --- |
| 承認 | 会場モニターへ流れる |
| 却下 | 破棄する。「非表示にした投稿」から復元もできる |
| 投稿者をブロック | 以降その投稿者の投稿を拾わない |

承認待ちは作業領域左の「運用」ナビと、上部ウォールバーのチップに件数が出ます
(1 件でもあると警戒色になります)。

## バックフィル (起動前の投稿を拾う)

サーバーを起動した時点より前の投稿も、Jetstream のカーソル再生機能で遡って取り込めます。
イベント開始前に告知タグで投稿してくれた人のコメントを、開場と同時に画面へ出せます。

**既定では起動時に取り込みを行いません** (`STARTUP_BACKFILL_MINUTES=0`)。
必要なときに管理画面の「受信設定」→「過去の投稿を取り込む」から実行します。

| 項目 | 内容 |
| --- | --- |
| 遡る分数 | 1〜2160 分 (約 36 時間) |
| 対象 | すべてのウォール / 選択中のウォールのみ |
| 実行中 | ライブ受信は止まらない。多重起動は拒否される |

イベント開始と同時に自動で埋めたい場合のみ、`.env` に値を入れます。

```dotenv
STARTUP_BACKFILL_MINUTES=120
```

| 遡る時間 | 取り込み完了までの実測時間 |
| --- | --- |
| 60 分 | 約 27 秒 |
| 120 分 | 約 90 秒 |
| 180 分 | 約 76 秒 |

取り込みは**ライブ受信とは別の WebSocket 接続**で並行して行われます。ライブ側は起動から
約 1 秒で新着投稿を受け始めるため、バックフィル中でもリアルタイム性は損なわれません。
取り込んだ過去投稿とライブ投稿が重複した場合は URI で重複排除されます。

### 削除された投稿の扱い

**バックフィルで取り込んだ投稿のうち、既に削除されているものは表示されません。**

過去分は取り込みが完了するまでサーバー側で保留し、再生中に届いた削除を反映してから
まとめて会場モニターへ送ります。1 本の接続で順に流すと「表示された数十秒後に消える」
ちらつきが起きるため、この方式にしています。運営が管理画面で非表示にした投稿も同様に除外されます。

実測 (4 時間の窓、2498 件が一致): うち削除済み 39 件を除外し、表示した 2459 件は
AppView 照合で全件が実在することを確認しています。

過去分は会場モニターの**既存カードより下**に時系列順で積まれるため、
ライブで流れている最新の投稿が押し下げられることはありません。

- 上限は Jetstream 側の保持期間で、実測でおよそ **36 時間** です。それより古いカーソルを
  指定しても保持境界に丸められ、エラーにはなりません。
- 遡る時間に比例して追いつくまでの時間が延びます。イベント用途では 60〜180 分が実用的です。
- 追いつくまでの間もリアルタイム受信は並行して進むため、投稿を取りこぼすことはありません。
- 保持件数は `BUFFER_SIZE` (既定 200) で頭打ちになります。長時間のバックフィルで古い投稿まで
  残したい場合は `BUFFER_SIZE` も上げてください。
- `0` にすると無効化され、起動時点以降の投稿のみを表示します。

なお、Bluesky の検索 API (`app.bsky.feed.searchPosts`) を使えばより長期間の遡及が可能ですが、
公開エンドポイントでは認証が必要 (未認証だと 403) なため、本システムでは採用していません。

## カスタムフィード (任意機能)

`FEED_GENERATOR_ENABLED=true` にすると、AT Protocol のカスタムフィード
(`app.bsky.feed.getFeedSkeleton`) を公開します。参加者が Bluesky アプリからも同じタグを
追えるようになりますが、公開するにはグローバルにアクセス可能な HTTPS ホスト名と
`did:web` の設定、フィードの publish 作業が別途必要です。会場内だけで使う場合は不要です。

## CI (GitHub Actions)

self-hosted runner で動く 2 つのワークフローがあります。

| ワークフロー | 生成物 | きっかけ |
| --- | --- | --- |
| `build` | 実行に必要なものだけを固めた `bsky-live-wall-<sha>.tar.gz` (LXC などへ置く用) | push (main) / タグ / PR / 手動 |
| `docker` | `ghcr.io/<owner>/bsky-live-wall` のイメージ | push (main) / タグ / PR (ビルドのみ) / 手動 |

`build` は型チェック・ビルド・テストを通してから固めます。中身は `dist/` と `public/`、
`package.json` / `pnpm-lock.yaml` / `.env.example` で、依存は展開先で
`pnpm install --prod --frozen-lockfile` して入れます (実行環境の Node と libc に
合わせて解決させるため)。タグを打つとリリースにも添付します。

runner には Node 24 以上と corepack (pnpm)、`docker` ワークフローを使う場合は
Docker と Buildx が必要です。

## リモートから使う (コンテナ / LXC)

サーバーで常時稼働させ、リモートから利用する場合の手順は
[docs/deployment.md](./docs/deployment.md) を参照してください。
Docker Compose (Caddy による TLS 自動取得)、Docker 単体、LXC + systemd の
3 通りの構成と、リバースプロキシの設定例を用意しています。

```bash
# 最短手順 (Docker Compose)
cp .env.example .env
# .env に HASHTAGS / ADMIN_TOKEN / WALL_DOMAIN を設定
docker compose up -d
```

リモート公開では、管理画面のログインを **AT Protocol OAuth** にできます。
共有トークンと違い、個人単位で識別・許可・失効ができます。

```dotenv
AUTH_MODE=oauth
PUBLIC_URL=https://wall.example.com
ADMIN_ACTORS=alice.bsky.social,bob.example.com
```

OAuth は本人確認までを担い、管理してよいかはこちらで決めます。スコープは `atproto` のみで、
パスワードは本システムに入力されません。

ログインできるのは次のいずれかです。

- `ADMIN_ACTORS` に載っているアカウント (最初の 1 人を通すための入口)
- **管理画面から招待したテナントのメンバー** (`.env` への追記は不要)
- `SYSTEM_ADMINS` のシステム管理者

ログインできても、操作できるのは自分がメンバーになっているテナントだけです
(何ができるかはそのテナントでの役割で決まります)。

**リバースプロキシ配下では `TRUST_PROXY=true` が必須です。** 設定しないと、
プロキシ経由のアクセスがすべて loopback と誤認され、`ADMIN_TOKEN` が空の場合に
誰でも管理 API を操作できてしまいます (このため `TRUST_PROXY=true` かつ
`ADMIN_TOKEN` 未設定では起動を拒否します)。

## UI の依存関係

| 画面 | 依存 |
| --- | --- |
| 会場モニター (`/wall`) | **依存ゼロ**。素の HTML / CSS / JavaScript のみ |
| 管理画面 (`/admin`) | Svelte 5 + Web Awesome (MIT) + Font Awesome Free |

会場モニターを依存ゼロに保っているのは、イベント当日の障害要因を増やさないためです。
管理画面は運営端末で使うもので、タブ・スイッチ・ダイアログ・フォーム部品を
自前で保守し続けるコストのほうが大きいため、コンポーネント集を使っています。

**どちらも CDN は参照しません。** 管理画面の依存は Vite がバンドルへ含めるため、
配信されるのは自己完結したファイルだけです。会場のネットワークが不安定でも表示が崩れません。

| 生成物 | サイズ |
| --- | --- |
| `public/admin/assets/*.js` | 約 350KB (gzip 約 95KB) |
| `public/admin/assets/*.css` | 約 200KB (gzip 約 41KB) |
| Font Awesome の webfont | 約 260KB |

### エディタでの補完

Web Awesome は `package.json` に `web-types` と `customElements` を宣言しているため、
JetBrains 系のエディタはカスタム要素の属性補完を自動で拾います。
VS Code で補完させたい場合は、`html.customData` に
`node_modules/@awesome.me/webawesome/dist/vscode.html-custom-data.json` を指定します。

なお、これらはエディタ向けのメタデータであり、**Svelte のコンパイラは読み込みません**。
ビルド時の警告とは無関係です。

### 管理画面のビルド

```bash
pnpm build      # サーバー (tsc) と管理画面 (vite) の両方
pnpm dev:admin  # 管理画面だけを watch ビルド
```

ソースは `src/admin/`、生成物は `public/admin/` (git 管理外) です。

`public/vendor/` は生成物のため git 管理外です。`pnpm install` 後に
`pnpm build`、`pnpm dev`、`pnpm vendor` のいずれかを実行すると作られます。

## アイコン

アイコンには Font Awesome Free を使います。**CDN は参照しません。**
会場のネットワークが不安定でも確実に表示させるため、Web Awesome のコンポーネント内でも `<wa-icon>` ではなく
`<i class="fa-solid ...">` を使います。アイコンの取得元設定を持ち込まずに済み、
オフライン動作の保証が崩れないためです。
