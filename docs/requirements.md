# 要件定義: Bluesky ライブウォール

## 1. 目的

イベント会場のモニター／スクリーンに、Bluesky 上の特定ハッシュタグ付き投稿をリアルタイムで表示する。
オンライン参加者のコメントを会場に可視化し、オンライン・オフライン双方の一体感を作る。

## 2. スコープ

| 区分 | 内容 |
| --- | --- |
| 対象 | Jetstream v2 からのリアルタイム受信、ハッシュタグ抽出、モデレーション、会場モニター表示、運営用管理画面 |
| 対象外 | 投稿機能（本システムから Bluesky へ投稿しない）、認証を要する API の利用、長期アーカイブ／分析基盤 |

## 2.1 ウォールの概念

「ウォール」は会場モニター 1 画面分の単位です。複数のモニターでそれぞれ別の語を拾えるよう、
1 つのサーバーで複数のウォールを扱います。

| 区分 | 内容 |
| --- | --- |
| ウォールごとに独立 | 監視語 / 投稿バッファ / 承認待ち / 表示設定 |
| 全ウォール共通 | ブロック / NG ワード / モデレーションリスト / 一時停止 / Jetstream 接続先 |

モデレーションを共通にしているのは、荒らしを 1 回ブロックすればすべてのモニターから
消えるようにするためです。画面ごとに個別のブロック操作を求めるのは運用上危険です。

## 3. 機能要件

### 3.1 収集 (Ingest)

- FR-01: Jetstream v2 (`wss://jetstream2.us-east.bsky.network/subscribe`) に WebSocket 接続し、`app.bsky.feed.post` のコミットを購読する。
  ウォールが複数あっても接続は 1 本のみとし、受信した投稿を各ウォールの監視語と
  突き合わせて振り分ける。接続を分けると同じ全量を何度も受信することになるため。
- FR-02: 切断時は指数バックオフ (最大 30 秒) で自動再接続する。再接続時は最後に受信した `time_us` を `cursor` として指定し、取りこぼしを最小化する。
- FR-03: プライマリホストへ規定回数連続で失敗した場合、フォールバックホスト (`jetstream1.us-east` / `jetstream1.us-west` / `jetstream2.us-west`) へ切り替える。
- FR-04: 対象ハッシュタグ (複数指定可) に一致する `create` コミットのみを採用する。判定は以下の OR で行う。
  - `record.facets[].features[]` の `app.bsky.richtext.facet#tag` の `tag` 値
  - `record.tags[]` (投稿レコードの tags フィールド)
  - `record.text` 中の `#タグ` のプレーンテキスト一致
  - 比較は Unicode 正規化 (NFKC) + 小文字化で行う。
- FR-04b: `STARTUP_BACKFILL_MINUTES` で指定された分だけ過去のカーソルから再生し、
  サーバー起動前の投稿を取り込む。Jetstream の保持期間 (実測およそ 36 時間) を超える指定は
  保持境界に丸める。**この再生はライブ受信とは別の WebSocket 接続で並行して行い**、
  追いつくまでの間もライブ投稿の表示を遅延させない。重複は URI で排除する。
  **既定は 0 (起動時には行わない)** とする。
- FR-04d: 運営が管理画面から、任意の時点で任意の分数の取り込みを実行できる。
  対象は全ウォールまたは特定のウォールを選べる。多重起動は拒否する。
  上限は Jetstream の保持期間に合わせて 2160 分 (約 36 時間) とする。
- FR-04c: バックフィルで取り込んだ投稿は再生完了までサーバー側で保留し、再生中に観測した
  削除コミットを反映してから送出する。既に削除された投稿を一度表示してから消す挙動を許容しない。
  確定した過去分は会場モニターの既存カードより下に時系列順で積む。
- FR-05: `delete` コミットを受信した場合、該当投稿が表示中なら即座に取り下げる。
- FR-06: 投稿者プロフィール (表示名 / ハンドル / アバター) を公開 AppView (`https://public.api.bsky.app`) から取得し、TTL 付きでキャッシュする。取得はバッチ (最大 25 件) でまとめる。
- FR-07: 画像 embed が付く投稿はサムネイル URL (`cdn.bsky.app`) を最大 4 枚まで保持する。

### 3.2 モデレーション

- FR-10: NG ワード (部分一致 / 正規表現) を含む投稿を破棄する。
- FR-11: ブロック DID / ハンドルの投稿を破棄する。
- FR-12: 投稿ラベル (`record.labels`) に成人向け等が付く投稿を破棄する。
- FR-13: リプライを表示対象に含めるかを設定で切り替えられる。
- FR-14: 運営が管理画面から、表示中の個別投稿を即時に非表示にできる。非表示にした投稿は
  再接続時のリプレイやバックフィルで再配信されても復活しない。
- FR-14b: 運営が管理画面から、非表示にした投稿を復元できる。ブロックを解除した場合は、
  ブロック時に取り下げた投稿もまとめて復元する。
- FR-15: 運営が管理画面から、ウォール全体を一時停止／再開できる。
- FR-16b: 運営が管理画面から監視対象を変更できる。変更は即座に反映され、
  上限はハッシュタグとキーワードの合計 20 件とする。表示中の投稿は残す (消去は別操作)。
- FR-16c: 監視対象はハッシュタグとキーワードの 2 種別を持つ。既定はハッシュタグで、
  明示的に指定した場合のみキーワード (本文の部分一致) として登録する。
  キーワードは 2 文字以上とする。
- FR-16d: 監視対象は種別が区別できる形で一覧表示し、個別に削除できる。
  削除は確認ダイアログを挟む。監視対象を 0 件にはできない。
- FR-16e: キーワードだけで一致した投稿は、既定で承認待ちに回す
  (`KEYWORD_REQUIRE_APPROVAL`)。ハッシュタグと違い、投稿者がイベントを
  認識していない可能性があるため。
- FR-16f: 承認待ちの投稿があるときは、モデレーションモードにかかわらず
  管理画面に承認待ちの一覧を表示する。表示条件をモードだけで決めると、
  `open` モードでキーワード一致した投稿が確認も承認もできなくなる。
- FR-17: 運営が管理画面から Jetstream の接続先を候補から選んで切り替えられる。
  切り替え時は直近のカーソルから再生し、取りこぼしを補填する。
- FR-18: 運営が自身のアカウントのモデレーションリストを購読でき、掲載アカウントの投稿を
  表示しない。リストは定期的に取り直す。取得に失敗した場合は前回の内容を使い続ける。
- FR-16: 承認モード (`MODERATION_MODE=approve`) では、運営が承認した投稿のみ会場モニターへ流す。

### 3.3 配信 (Distribution)

- FR-20: 表示クライアントへは Server-Sent Events (SSE) で push する。ページ再読み込みなしで流し続けられること。
- FR-21: 接続直後に直近 N 件 (既定 30 件) のバックログを送出し、画面が空にならないようにする。
- FR-22: ハートビートを 15 秒間隔で送出し、プロキシによる無通信切断を防ぐ。
- FR-23: クライアント側は切断を検知して自動再接続する (`EventSource` 標準動作 + 明示的な再接続)。
- FR-24: 任意機能として AT Protocol カスタムフィード (`app.bsky.feed.getFeedSkeleton`) のエンドポイントを提供し、参加者が Bluesky アプリからも同じタグを追えるようにする。

### 3.4 表示 (会場モニター)

- FR-30: ブラウザ全画面表示 (1920x1080 を基準、4K でも破綻しないこと) を前提とする。
- FR-31: 文字サイズは会場後方からの視認を前提とし、`vw`/`vh` ベースの相対指定で拡縮する。本文は最低でも画面高の 2.5% 相当。
- FR-32: 新着投稿はアニメーション付きで挿入され、古い投稿が押し出される。フリッカーを起こさないこと。
- FR-33: 長文は指定行数で省略し、レイアウトを崩さない。
- FR-34: 画面には対象ハッシュタグ、接続状態、表示件数を常時表示する。
  表示件数は現在の表示実績を表し、投稿者による削除および運営による非表示は差し引く。
  画面の全消去では減らさない (表示した事実を取り消すものではないため)。
- FR-34b: `/wall/<id>` で個別のウォールを開く。`/wall` は既定ウォールを開く。
  会場モニターにはウォール名を表示し、どの画面を映しているか分かるようにする。
- FR-35: レイアウトは既定で 1 カラムの縦流れとし、新着が上から入って古い投稿を下へ押し出す。
  カラム数は設定で変更可能で、2 以上を指定した場合のみ横並びのグリッドになる。
- FR-36: 数時間の連続稼働でメモリリークやパフォーマンス劣化を起こさないこと (DOM ノード数を上限で打ち切る)。
- FR-37: マウスホイールで過去の投稿へスクロールできる。スクロール中に新着が届いても読んでいる
  位置をずらさず、未読件数を表示する。60 秒間操作がなければ自動的に先頭へ戻り追従を再開する。

### 3.5 管理画面

- FR-40: 直近の受信投稿一覧、非表示操作、一時停止、承認操作を提供する。
- FR-40b: ウォールの作成・改名・削除ができる。既定ウォール (`.env` から作られる) は
  削除できない。ウォールは 10 個まで。
- FR-40c: 管理画面はウォールを切り替えて操作できる。ウォール単位の操作と
  全ウォール共通の操作を、運営が取り違えないよう明示する。設定パネル自体も
  スコープごとに分ける (ウォール単位の設定の中に共通設定を混ぜない)。
- FR-40d: ウォールの切り替えはタブとする。タブが画面幅を超えた場合は
  タブ列のみが横スクロールし、ヘッダの高さが変わらないこと。
  選択中のタブが隠れている場合は自動的に表示範囲へ寄せる。
- FR-44: すべてのテキスト入力で、IME の変換確定 Enter を送信として扱わない。
  日本語・中国語・韓国語の入力で誤送信が起きるため、変換中かどうかを
  判定してから確定操作を行う。
- FR-41: 管理画面はトークン (`ADMIN_TOKEN`) による簡易認証で保護する。
- FR-42: リバースプロキシ配下 (`TRUST_PROXY=true`) では、トークンなしの loopback 例外を
  無効化し、`ADMIN_TOKEN` 未設定なら起動を拒否する。プロキシ経由のアクセスが loopback と
  誤認されることによる認証バイパスを防ぐ。
- FR-43: 管理 API の認証失敗が同一 IP から一定回数を超えた場合、一時的に拒否する。
- FR-44: 管理画面はトークンをブラウザに保存しない。ログイン時に一度だけ検証し、
  以降は HttpOnly Cookie のセッションで認証する。セッションには有効期限を設ける。
- FR-45: 運営はすべてのセッションを即座に失効できる (トークン漏洩時の緊急手段)。
- FR-46: Cookie 認証における CSRF を防ぐため、状態変更操作にはカスタムヘッダを要求する。
- FR-47: 管理操作を監査ログに記録する (操作内容・時刻・IP・セッション識別子)。
- FR-48: リモート公開時 (`TRUST_PROXY=true`) にトークンが規定長未満なら起動を拒否する。
- FR-49: 管理画面は AT Protocol OAuth によるログインに対応する。要求スコープは `atproto`
  のみとし、利用者のパスワードを本システムで扱わない。
- FR-50: OAuth は本人確認のみを担う。管理の可否は `ADMIN_ACTORS` の許可リスト (DID で判定)
  で決める。リストにないアカウントはセッションを発行しない。
- FR-51: 許可リストは運用中に再読み込みでき、外されたアカウントのセッションは即座に失効する。
- FR-52: OAuth 使用時に必須設定 (`PUBLIC_URL` の存在と https、`ADMIN_ACTORS` の非空) を
  起動時に検証し、満たさない場合は起動を拒否する。
- FR-53: `AUTH_MODE=oauth` ではトークンに関するすべての経路 (Bearer 認証、トークンログイン、
  トークン未設定時の loopback 例外) を無効化する。loopback 例外はトークン方式の利便機能であり、
  認証方式として独立して成立してはならない。

## 4. 非機能要件

- NFR-01: 投稿から会場表示までの遅延は通常時 2 秒以内を目標とする。
- NFR-02: 単一プロセスで動作し、会場 LAN 上の 1 台の PC でも運用できること。
- NFR-03: 外部依存は Jetstream と公開 AppView のみ。Bluesky アカウントの認証情報を必須としない。
- NFR-04: 状態はメモリ上のリングバッファで保持する。永続化は任意 (JSON Lines への追記)。
- NFR-05: 設定はすべて環境変数 (`.env`) から与える。ハードコードしない。

## 5. 運用シナリオ

1. 運営が `.env` にイベントのハッシュタグを設定してサーバーを起動する。
2. 会場 PC のブラウザで `http://<host>:<port>/wall` を開き、F11 で全画面にする。
3. 運営端末で `http://<host>:<port>/admin` を開き、必要に応じて非表示・一時停止を行う。
4. イベント終了後、サーバーを停止する。
