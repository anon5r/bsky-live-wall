# ロードマップ: マルチテナント化と機能拡張

本書は「サーバーのマルチテナント化」計画のレビューと、そこから導いた設計方針・追加機能の
提案・段階的な実装計画をまとめたものです。

## 0. 前提として実測した事実

設計判断の根拠として、計画立案時点で以下を実測しています。

| 項目 | 実測値 | 出典 |
| --- | --- | --- |
| Jetstream のライブ流量 (投稿作成) | 約 27 件/秒 | 30 秒間の実測 |
| Jetstream のライブ流量 (削除含む合計) | 約 35 件/秒 | 同上 |
| Jetstream の再生速度 | 約 3,200 件/秒 | 60〜480 分のバックフィル実測 |
| Jetstream の保持期間 | 約 36 時間 | 48/168 時間指定が 36 時間に丸められることを確認 |
| `app.bsky.graph.getLists` / `getList` | **認証なしで取得可能** (modlist / curatelist、ページング可) | public AppView で確認 |
| `app.bsky.actor.getProfiles` の取得項目 | `createdAt` (アカウント作成日) / `followersCount` / `postsCount` / `labels` を含む | 同上 |
| `app.bsky.feed.searchPosts` | **認証が必要** (未認証は 403) | 同上 |

## 1. 計画のレビュー

### 1.1 AT Protocol アカウントでのログイン

**判断: 賛成。ただし atproto OAuth を使い、アプリパスワードは採用しない。**

アプリパスワードはアカウント全権に近い権限を渡すことになり、第三者サービスが預かるべきものでは
ありません。atproto OAuth であればスコープが限定され、ユーザー側でいつでも失効できます。

**ただし、これは前提条件を根本から変える変更です。** 現在の設計は「会場 PC 1 台で完結し、
認証情報を一切必要としない」ことを最大の強みにしています (NFR-02 / NFR-03)。OAuth は
公開された HTTPS ホストとクライアントメタデータ文書の常時配信を必要とするため、
会場ローカル完結を維持できません。

**推奨: 2 つの動作形態を明示的に分ける。**

| 形態 | 用途 | 認証 | 設定 |
| --- | --- | --- | --- |
| スタンドアロン (現行) | 単一イベント、会場 PC で運用 | 不要 | `.env` |
| マネージド (新規) | 複数イベント、共用サーバー | atproto OAuth | Web UI |

スタンドアロンを残すことは冗長ではなく、**当日の障害対策**です。マネージド側やネットワークに
問題が出たとき、会場 PC でスタンドアロンを起動すれば復旧できます。コードベースは共通化し、
起動モードで切り替えます。

### 1.2 ハッシュタグ以外のワード抽出

**判断: 条件付きで賛成。ただし既定は無効とし、有効化時は承認モードを強制する。**

これは技術的な話ではなく**同意の問題**です。

- ハッシュタグ付き投稿は、投稿者が「このイベントの場に出す」意思を明示したものです。
- 任意のワード一致は、**イベントを知らない第三者の投稿を会場スクリーンに晒す**ことになります。
  「#」を付けていない人はイベントへの参加意思を示していません。

会場に無関係な個人の投稿が大写しになる事故は、技術的な不具合より深刻な問題になり得ます。

**推奨する制約:**

- 既定はハッシュタグのみ。任意ワードは明示的に有効化する。
- 任意ワードを 1 つでも設定したイベントは、`MODERATION_MODE` を自動的に `approve` に固定する
  (設定で緩和できないようにする)。
- 最小文字数を 3 文字以上とし、極端に一般的な語 (助詞、`the` など) は拒否する。
- マッチ率の上限を設け、単位時間あたりの一致数が閾値を超えたら自動的にそのワードを停止して
  管理者に通知する (誤設定・濫用の自動遮断)。

### 1.3 イベントごとの設定保持・複数ストリーム

**判断: 賛成。ただし「ストリーム」という語を分解して定義する。**

計画中の「ストリーム」が指すものが曖昧です。以下 3 つを分けて設計してください。

| 概念 | 実体 | ライフサイクル |
| --- | --- | --- |
| イベント設定 (Event) | タグ、ワード、モデレーション設定、表示設定 | 永続。使い回す |
| 実行中セッション (Session) | 受信中の状態、投稿バッファ、統計 | イベント期間中のみ |
| 表示クライアント (View) | ブラウザの接続 | 接続中のみ |

「イベントが終了するとストリームは削除される」は、**セッションの破棄であって設定の削除ではない**
という理解でよいはずです。設定が消えると翌年の同じイベントで作り直しになります。

### 1.4 Lexicon を使ってユーザーの PDS に設定を保存する

**判断: 部分的に反対。少なくとも v1 では採用しない。**

魅力的なアイデアですが、次の問題があります。

1. **PDS のレコードは公開されます。** NG ワード、ブロック対象、運営メモがすべて第三者から
   読めます。NG ワード一覧の公開は、荒らしにフィルタの回避方法を教えることと同じです。
   これは単独で採用を見送るに足る理由です。
2. **スキーマ変更の後戻りができません。** レコードはユーザーの PDS 上にあるため、こちらから
   一括マイグレーションできません。仕様が固まっていない段階で公開レコードを撒くと、
   互換性維持のコストを長期間背負います。
3. **NSID に自分の管理下のドメインが必要**で、名前空間の設計をやり直しにくい。
4. **PDS 障害・レート制限**が設定読み込みの障害点になります。イベント当日に設定が読めない
   リスクを増やす判断は避けるべきです。

**推奨: 保存先を機微性で分ける。**

| データ | 保存先 | 理由 |
| --- | --- | --- |
| イベント名、ハッシュタグ、開催時間、表示設定 | サーバー DB (将来 PDS へも書き出し可) | 公開されても困らず、共有価値がある |
| NG ワード、個別ブロック、運営メモ | **サーバー DB のみ** | 公開されると機能が無効化される |
| 参照するモデレーションリストの URI | サーバー DB | リスト自体は既に公開されている |

PDS 保存は **v2 以降に「設定のエクスポート/インポート」機能として**追加するのが安全です。
スキーマが実運用で安定してから公開レコードにするほうが、後戻りコストが小さくなります。

### 1.5 モデレーションリストによるブロック

**判断: 賛成。実現可能なことを実測で確認済み。**

`app.bsky.graph.getList` は認証なしで `modlist` のメンバーを取得でき、ページングにも対応して
います。ユーザー自身のリスト一覧も `app.bsky.graph.getLists?actor=<did>` で取得できます。

**設計上の注意:**

- リストは数千〜数万件になり得ます。DID の `Set` に展開してメモリ保持し、
  投稿判定は O(1) にします。
- イベント中にリストへ追加された相手を反映するため、**定期的な再取得** (5 分間隔程度) が必要です。
  即時反映が要るなら、管理画面から手動再取得もできるようにします。
- 複数リストの指定を許可します (自分のリスト + 他者の公開リストの購読)。
- リスト取得失敗時に**投稿表示を止めてはいけません**。前回取得分を使い続け、管理画面に警告を出します。
- `curatelist` も指定できるようにすると、「登壇者リスト」「スタッフリスト」を優先表示・
  常時表示するといった使い方ができます (1.6 の追加提案を参照)。

### 1.6 イベント終了時の挙動

**判断: 定義が粗い。以下を明示的に決める必要があります。**

- **猶予時間**: イベントは押します。終了時刻の到来で即座に切るのではなく、既定 30 分の猶予を
  設け、管理画面から延長できるようにします。
- **終了時の画面**: 突然真っ黒になるのは避け、「ご参加ありがとうございました」+ サマリーへ
  切り替えます。
- **破棄の対象**: 受信を停止し、表示データを破棄します。**イベント設定と統計サマリーは残します。**
- **自動終了の上限**: 終了時刻が設定されていないイベントも 24 時間で自動終了させ、
  放置されたセッションがリソースを占有しないようにします。

### 1.7 マルチテナントの受信設計 (計画に記載がないが最重要)

**テナントごとに Jetstream 接続を張ってはいけません。**

Jetstream にはサーバー側のタグ絞り込み機能がありません。接続を N 本張ると、
**同じファイアホース全量を N 回受信する**ことになり、帯域と Jetstream 側の負荷が N 倍になります。

**推奨: 1 本の共有接続 + キーワード逆引きインデックスでファンアウトする。**

```text
          1 本の Jetstream 接続 (約 27 件/秒)
                     |
              正規化 & タグ抽出
                     |
        キーワード -> イベント の逆引き Map
           |          |          |
      Event A    Event B    Event C  (それぞれのモデレーション・バッファ)
```

実測流量が約 27 件/秒であるため、CPU は事実上問題になりません。仮に全テナント合計で
1,000 個のキーワードを登録しても、単純な照合で毎秒 27,000 回の比較にしかならず、
最適化なしで処理できます。ボトルネックはむしろ**バックフィルの同時実行** (再生は約 3,200 件/秒)
なので、バックフィルはイベント単位でキューイングし、同時実行数を制限してください。

### 1.8 計画に不足している論点

| 論点 | 内容 |
| --- | --- |
| **誰がイベントを作れるか** | 「Bluesky アカウントがあれば誰でも」だと、公開後に濫用されます。初期は招待制または許可リストにすべきです |
| **上限値の具体化** | 「上限あり」とだけ書かれています。下記 2.2 に具体案を示します |
| **テナント間の分離** | あるイベントの管理者が他のイベントの投稿・設定を読めないことを、API 設計とテストで保証する必要があります |
| **データ保持期間** | 統計サマリーをいつまで保持するか。個人情報保護の観点から明示が必要です |
| **費用** | 常時稼働するサーバーの費用負担者。無償公開なら濫用対策が必須です |

## 2. 設計方針 (決定事項の案)

### 2.1 動作形態

- スタンドアロン (現行) を維持する。マネージドは同一コードベースの別起動モードとする。
- マネージドは atproto OAuth を採用し、アプリパスワードは受け付けない。
- 受信は全テナントで 1 本の Jetstream 接続を共有する。

### 2.2 上限値 (初期案)

| 対象 | 上限 | 根拠 |
| --- | --- | --- |
| ユーザーあたりの保存イベント設定 | 20 | 通常の主催者には十分 |
| ユーザーあたりの同時実行イベント | 3 | 並行トラックのあるカンファレンスを想定 |
| イベントあたりのハッシュタグ | 10 | 表記ゆれの吸収に必要な数 |
| イベントあたりの任意ワード | 5 | 承認モード強制のため運用可能な範囲 |
| 任意ワードの最小文字数 | 3 文字 | 過剰一致の防止 |
| イベントあたりの参照モデレーションリスト | 5 | |
| イベントの最大継続時間 | 24 時間 | 放置セッションの自動終了 |
| バックフィルの同時実行 | 2 | 再生が高速なため待ち行列で足りる |

### 2.3 データモデル (概略)

```text
User        did, handle, 作成日時, 権限
Event       id, ownerDid, 名称, 開始/終了時刻, 状態, 表示設定
Keyword     eventId, 種別(hashtag|word), 値, 正規化値
ModList     eventId, listUri, 最終取得時刻
Blocklist   eventId, did, 追加者, 追加日時       ← 手動ブロック
NgWord      eventId, 値, 種別(substring|regex)   ← 公開しない
Summary     eventId, 統計, 生成日時              ← 終了時に生成
```

## 3. 追加機能の提案

イベント進行の実務から見て効果が大きい順に挙げます。

### 3.1 優先度 高

**(1) QR コードによる投稿導線**

会場モニターと待機画面に、ハッシュタグを添えた投稿画面へのリンクを QR コードで常時表示します。
「ハッシュタグを手で入力してください」と言うだけの場合と比べ、参加率が明確に変わります。
QR は外部サービスに頼らず、依存のない自前生成でオフライン動作させます。

**(2) 新規アカウント・低フォロワーのフィルタ**

荒らしの主要経路は捨てアカウントです。`app.bsky.actor.getProfiles` から
`createdAt` (アカウント作成日) と `followersCount` が**認証なしで取得できることを実測済み**です。

- 「アカウント作成から N 日以内の投稿は非表示」
- 「フォロワー N 人未満の投稿は承認待ちに回す」

実装コストが小さく、効果が大きい対策です。既存のプロフィール取得処理に判定を足すだけで済みます。

**(3) 同一投稿者のレート制限**

1 人が連投して画面を占有するのを防ぎます (例: 同一 DID は 5 分あたり 3 件まで表示)。
悪意がなくても実況好きな参加者 1 人で画面が埋まる事故は起きます。

**(4) 運営アナウンスの差し込み**

Bluesky を経由せず、管理画面から直接ウォールへメッセージを出します。
「10 分休憩」「次のセッションは B 会場」「避難経路の案内」など、進行に直結します。
Bluesky 側に投稿すると恒久的に残ってしまう内容を、その場限りで出せることに意味があります。

**(5) パニックボタン**

1 アクションで「全消去 + 一時停止 + 中立画面への切り替え」を行います。
個別の非表示操作は、問題が起きてから探す時間が発生します。まず画面を止め、
落ち着いてから個別対応するほうが安全です。管理画面とキーボードショートカットの両方に割り当てます。

### 3.2 優先度 中

**(6) 配信オーバーレイモード**

`?transparent=1` で背景を透過し、OBS 等のブラウザソースとして配信画面に重ねられるようにします。
オンライン参加者の反応を配信にも載せられるため、「オンラインとオフラインの一体感を作る」
という本来の目的に直結します。

**(7) 表示モードの追加**

| モード | 用途 |
| --- | --- |
| カードウォール (現行) | メインスクリーン |
| ティッカー | 画面下部を 1 行で流す。登壇中のサブ表示 |
| 単発大表示 | 1 件を全画面で数秒ずつ。休憩中の場つなぎ |

**(8) ピン留め**

重要な投稿 (登壇者の告知、公式アナウンス) を画面上部に固定します。

**(9) Q&A レーン**

`#質問` のような専用タグを別枠として扱い、承認したものだけを右側などに分けて表示します。
カンファレンスでは質疑応答の運用が課題になりやすく、価値が高い機能です。

**(10) 画像の即時オフ**

現在 `SHOW_IMAGES` は環境変数のみで、変更に再起動が要ります。管理画面のトグルにします。
不適切な画像が出たときの一次対応として、再起動を挟まず全画像を止められることが重要です。

### 3.3 優先度 低 (あると喜ばれる)

**(11) 終了サマリー**

投稿数の時系列グラフ、投稿者ランキング、頻出語。主催者が事後に共有できる形で出します。

**(12) アーカイブ書き出し**

CSV / JSON。ハッシュタグの利用実績を記録として残したい主催者向け。

**(13) 会場モニターのキーボードショートカット**

一時停止、先頭へ戻る、モード切替。運営が壇上から操作する場面を想定します。

**(14) 表示言語の切り替え**

国際イベント向けに UI 文言を切り替えます。投稿本文の翻訳は行いません
(誤訳を大画面に出すリスクのほうが大きいため)。

## 4. 段階的な実装計画

各フェーズは単体で価値が出る単位に区切っています。

### フェーズ 1: スタンドアロンの完成度を上げる (マルチテナント化の前)

マルチテナント化に着手する前に、単一イベントでの運用品質を固めます。
ここで得た知見がマルチテナントの設計に反映されます。

- 新規アカウント・低フォロワーのフィルタ (3.1-2)
- 同一投稿者のレート制限 (3.1-3)
- QR コードによる投稿導線 (3.1-1)
- 運営アナウンスの差し込み (3.1-4)
- パニックボタン (3.1-5)
- 画像の即時オフ (3.2-10)
- モデレーションリスト連携 (1.5) — 設定は `.env` でリスト URI を指定する形から始める

### フェーズ 2: 受信基盤のマルチテナント対応

UI を伴わない内部構造の変更のみを行い、スタンドアロンの動作を変えません。

- 1 本の共有 Jetstream 接続 + キーワード逆引きインデックス
- イベント / セッション / ビューの分離
- バックフィルのキューイングと同時実行制限
- テナント分離のテスト

### フェーズ 3: 認証と管理 UI

- atproto OAuth (招待制または許可リストで開始)
- イベント設定の CRUD、開始/終了スケジュール
- モデレーションリストの UI からの指定
- 上限値の適用

### フェーズ 4: 運用機能の拡充

- 終了サマリーとアーカイブ書き出し
- 配信オーバーレイモード、表示モードの追加
- Q&A レーン、ピン留め

### フェーズ 5: 設定の可搬性 (任意)

- 設定の PDS へのエクスポート/インポート (lexicon の設計はここで確定させる)
- 公開しても差し支えない項目に限定する

## 5. 未解決の論点

決める必要があるが、まだ判断材料が足りない項目です。

1. **公開範囲**: 招待制で運用するのか、誰でも使える公開サービスにするのか。
   後者の場合、濫用対策と費用負担の設計が先に必要です。
2. **イベント設定の共有**: 共同運営者を追加できるようにするか。カンファレンスでは
   1 人の主催者アカウントに依存すると当日に詰みます。読み取り専用の共同管理者は用意すべきです。
3. **統計サマリーの保持期間**: 投稿者のハンドルを含むため、保持期間と削除方法を明示する必要があります。
4. **削除された投稿の扱い**: 現在はバックフィル時に除外していますが、サマリーやアーカイブに
   含めるかは別途判断が要ります。投稿者が消したものを記録に残すのは避けるべきです。
5. **ラベラー連携**: Bluesky のラベラー (モデレーションサービス) を購読して自動除外に使うか。
   モデレーションリストより網羅的ですが、依存先が増えます。
