# マルチテナント化の設計 (段階 2)

段階 1 (運用モードのフラグ、URL 形状、テナント永続化層) は実装済み。
本書は段階 2 (受信基盤をテナント単位へ広げる) の設計をまとめる。

## 1. 構成

```text
  IngestHub (サーバー全体で 1 個)
    ├ JetstreamClient   ライブ受信 (1 本)
    ├ BackfillReader    過去の取り込み (1 本、同時 1 件)
    └ ProfileHydrator   プロフィール解決 (全テナント共有キャッシュ)
         |
         | commit / profile / status
         v
  TenantRegistry
    ├ single モード: .env から 1 テナント (DB 不使用)
    └ multi  モード: TenantStore が出どころ
         |
         +--> TenantRuntime A  (= WallSource)
         |      ├ Wall A-1, A-2 ...   監視語 / 投稿バッファ / 承認待ち
         |      └ モデレーション       ブロック / 非表示 / リスト / 一時停止
         +--> TenantRuntime B
```

**接続はテナントが増えても 1 本のまま。** テナントごとに張ると同じ全量を
何度も受信することになり、帯域と相手側の負荷が無駄に増える。
実測のライブ流量は約 27 件/秒なので、突き合わせの CPU は問題にならない。

## 2. 共有と分離の境界

| 範囲 | 対象 |
| --- | --- |
| サーバー全体で共有 | Jetstream 接続 / 接続先ホスト / プロフィール解決のキャッシュ / バックフィルの実行枠 |
| テナントごと | 設定 (NG ワード・言語・承認モード等) / ブロック / 非表示 / モデレーションリスト / 一時停止 / メンバー |
| ウォールごと | 監視語 / 投稿バッファ / 承認待ち / 表示設定 / 承認モード (テナント設定を継承可) |

単一テナント運用では「テナントごと」の層が 1 つしかないため、
現在の挙動と変わらない。

## 3. バックフィルの扱い

接続が 1 本しかないため、過去の取り込みは**サーバー全体で同時 1 件**に限る。

- `IngestHub.startBackfill({ minutes, owner })` の `owner` は要求元のテナント ID
- 再生中の commit には `backfillOwner` が付き、**要求元のテナントにしか配らない**
- 実行中の別要求は拒否する (待ち行列は作らない)

テナントが多い環境では待たされることになるが、招待制の小規模運用が前提のため
まずはこれで足りる。足りなくなったら待ち行列を足す。

## 4. 設定の出どころ

| モード | 出どころ | 変更の反映 |
| --- | --- | --- |
| single | `.env` | メモリ上のみ。再起動で `.env` に戻る |
| multi | `TenantStore` (SQLite) | 永続化され、再起動後も残る |

`TenantRuntime.updateSettings()` はモードによって書き込み先を変える。
呼び出し側 (server 層) はモードを意識しない。

## 5. 認可

### 役割

| 役割 | 指定 | できること |
| --- | --- | --- |
| システム管理者 | `.env` の `SYSTEM_ADMINS` | 全テナントの管理・作成・削除、接続先の切り替え、監査ログ全体 |
| テナント owner | メンバー表 | そのテナントの設定・ウォール・メンバー管理 |
| テナント moderator | メンバー表 | そのテナントの運用操作のみ |
| ログイン可能 | `ADMIN_ACTORS` + テナントのメンバー表 + `SYSTEM_ADMINS` | 最初の 1 人は `.env`、以後は管理画面からの招待 |

**システム管理者を DB ではなく `.env` で持つ**のは、テナントが 1 件も無い初期状態でも
管理者が存在する必要があり、DB が壊れても締め出されないため。起動時にハンドルを
DID へ解決する。システム管理者はすべてのテナントで owner 相当として扱う。

Jetstream の接続先は全テナント共有のため、multi モードではテナント側からの
切り替えを禁止し (403)、システム管理 API に集約する。

### 旧記述

- multi モードでは `AUTH_MODE=oauth` が必須 (実装済み)
- テナントの操作可否は `TenantRuntime.getMemberRole(did)` で判定する
- `owner` は設定変更まで、`moderator` は運用操作のみ
- グローバルな `ADMIN_ACTORS` は single モード専用とし、
  multi ではテナントごとのメンバーを使う

## 6. 段階的な進め方

| 段階 | 内容 | 状態 |
| --- | --- | --- |
| 2-a | `IngestHub` の抽出。`WallManager` から Jetstream / バックフィル / プロフィール解決を分離する | **完了** |
| 2-b | `TenantRuntime` 化。残った `WallManager` をテナント単位にする | **完了** |
| 2-c | `TenantRegistry`。single は `.env` から 1 件、multi は `TenantStore` から | **完了** |
| 2-d | server 層のテナント解決。`/e/:eventId` から `TenantRuntime` を引く | **完了** |
| 2-e | 管理 API のテナント対応と権限判定 | **完了** |
| 3-a | システム管理者・メンバー管理・システム管理 API | **完了** |
| 3-b | 管理画面のテナント選択・メンバー管理・システム管理画面 | **完了** |

**2-a から 2-c までは単一テナントの挙動を変えないこと。** 既存の検証が
そのまま通る状態を保ったまま内部構造だけを移す。

### 2-d / 2-e で解消したこと

`createServer` は `WallSource` ではなく `TenantRegistry` を受け取るようになった
(`createWallSource` は不要になり削除)。ルートは「テナントに属する」
(`/api/stream`・`/api/posts`・`/api/admin/state` など、ルート直下と
`/e/:eventId/` の両方に登録) と「テナントに属さない」
(`/api/health`・`/api/auth/*`・`/api/admin/session*`・`/api/admin/tenants*`) に
分け、前者は `request.tenant` (`src/server/tenant-context.ts`) にテナントを
積む `onRequest` フックを経由する。single モードのルート直下は既定テナントに、
multi モードのルート直下は 404 (`tenant_required`) になる。

これにより multi モードは**テナントが 1 件も無い状態でも起動できる**
(ヘルスチェックはテナント数に依存しない)。

権限判定は `src/server/permission.ts` の `checkTenantPermission` で行い、
`/api/admin/*` の各ハンドラが `TenantRuntime.getMemberRole(did)` を通して
呼び出す。DID を伴わない Bearer トークン認証 (`ADMIN_TOKEN`) では
「どのテナットの誰か」を特定できないため、multi モードのテナントに属する
操作は一律で 403 にしている
(`AUTH_MODE=both` を multi で使うこと自体は許可しているが、
Bearer はテナントに属さない API — ヘルスチェックやセッション管理など — にしか実質的に使えない)。


## 7. 未検証の範囲

マルチテナントでは OAuth ログイン (DID を伴うセッション) が前提のため、
トークンログインでは次を実地で確認できていない。

| 項目 | 状態 |
| --- | --- |
| OAuth でのログインとテナント選択 | 未検証 (OAuth の実環境が必要) |
| メンバーの追加・役割変更・削除の実操作 | 未検証 (API 単体の権限判定は検証済み) |
| システム管理画面からのテナント作成・削除 | 未検証 (同上) |

権限判定そのもの (システム管理者の判定、非メンバーの拒否、オーナー 0 人の防止) は
`TenantStore` と `permission.ts` を直接呼ぶ形で検証済み。
残るのは HTTP とブラウザを通した経路の確認で、`SYSTEM_ADMINS` に自分のハンドルを
設定して OAuth でログインすれば一通り試せる。
